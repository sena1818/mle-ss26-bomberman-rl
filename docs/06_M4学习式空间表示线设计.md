## 0. v1 → v2 的六处协议修复

v1 的训练内核（表示、CNN、Double DQN、n-step、D4、uint8 replay）经审查判定可靠，
**协议不可靠**。以下六项在动用二十多个 CPU 小时之前修完，每一项都先复现再动手：

| # | 问题 | 修法 |
|---|---|---|
| 1 | **吞吐低估 2.1×**：`benchmark_cnn` 只计时 `fit_batch`，而 Double DQN 一次更新的大头是两次 next-state 前向 | 改测完整 learner 路径。**20.34 ms/梯度步，不是 9.59**；3M steps **4.4 h/seed** |
| 2 | **「调用 learner」与「真的做了梯度」同一个计数器**；buffer 未满时返回 `0.0`，与「TD error 恰好为零」不可分辨 | learner 返回 `gradient_applied` / `gradient_steps` / `replay_size`；CNN additionally 报 `loss`、裁剪前梯度范数、Q 统计（全部从已有张量读出，零额外成本） |
| 3 | **`coins_share` 是 G-B 判据，聚合器根本没算它** | 加入 `ALL_METRICS`；分母为零时返回 undefined 而非 0 |
| 4 | **checkpoint 选择在 `train_seed × round` 上取最大值**（M4 每臂 100 个策略），winner's curse | 先按 round 池化五个 seed → 在 **validation** 曲线上选 round → 冻结 → 报该 round 的五 seed 分布 → 才读 holdout。`selected_checkpoint` 保留但在产物里明确标注为「仅供提交选型，不可引用」 |
| 5 | **G-A 要求 holdout 曲线单调上升**：既不现实，又把 holdout 用掉了 | 改成 validation 上的窗口趋势 + 非退化下限，holdout 完全不参与 |
| 6 | **一臂 1,265 个 job**，其中 600 个是最慢且不可复现的对手评估 | 新增 `mode: "rounds"` 显式指定评估轮次。**一臂 335 个 job，对手评估 90 个** |

另外，审查把**对手暴露**提到了 dueling 之前，理由见 §8；已作为独立配置落地。

**为什么这不是放宽门槛，而是修一个写错的断言：**

1. `round_end_reason` 的 docstring 明写这个近似 **unavoidable**——`time_to_stop` 要求

2. `experiment.py:326` 的注释本身写着「**Only** the smoke-stage approximation can cause this」。
3. **项目先例**：§0.18 里 `M3.9` 有 **17** 次，被确认为同一近似而**接受**了。

**两个方向为什么必须分开**（这正是 docstring 对 TASK_COMPLETE / TRUNCATION 说的

| 分支 | 含义 | 判定 |
|---|---|---|
| `predicted_early`（`experiment.py:328`） | 预测终止但回合继续。只在**没东西可收、没箱子、没炸弹、没对手**时触发——真实剩余回报本来就是零，`target = r` 反而是对的 | **报告**，并记录预测原因；原因不是 `TASK_COMPLETE` 就失败 |
| `unpredicted`（`experiment.py:388`） | 框架结束了 runtime 没预测到的回合。**那条 transition 用了 bootstrap，本该是 `target = r`** | **硬失败** |

**另外两处不是覆盖、而是新增的硬约束**（v2 中不存在）：

- **对手臂的判定必须用重复测量**（≥5 次重跑末 checkpoint 的对手评估）——§0.20 方法note 1。

## 1. 这条线要回答什么

`docs/05` §0.13 量出的 `handcrafted_v3` 「致命岔路不可分辨率」：

| 口径 | v3 不可分辨率 |
|---|---:|
| loot-crate solo（训练任务） | **0%** |
| **`classic` + 3 对手（比赛设置）** | **34.7%** |

**一条必须说准的界限。**这个数字来自 `diagnose_bomb_escape.py`，它比较的是
**`escape_by_direction` 这一个子块**，不是完整的 `(状态向量, 动作)`。它证明的是
「**为回答这个问题而设计的那组特征分不开致命方向和救命方向**」，
**不是**「任何学习规则都不可能区分」——状态向量的其它维度仍可能带有区分信息。
它是很强的缺失特征提示，不是不可能性定理。**报告里必须按这个较弱的读法写。**

在较弱的读法下结论仍成立：**手工线在训练任务上已无可测的表示瓶颈，在比赛设置上还有。**
这是 M4 唯一有理论依据的优势区。

### 判定（取代 §5.2 的「9/14 未追平 M3 则冻结」）

| | 判据 | 依据 |
|---|---|---|
| **G-A 必达** | 能从零学，**只在 validation 上判**。三条同时成立：<br>(a) 末两个 checkpoint 均值 − 前两个均值 **> 4.7**；<br>(b) 末段高于未训练 CNN 对照（smoke 实测 score 0.0、`wait_fraction` 0.93、`distinct_cells` 1.78）；<br>(c) 不退化：`distinct_cells` > 20、`bomb_rate` > 0.01、`wait_fraction` < 0.6 | **不要求逐点单调**：RL 曲线中途回落是正常的，拿它当失败判据会误杀一个正在学的 agent。**holdout 不参与这个决定**，否则它就不再是 holdout |
| **G-B confirmatory** | `classic` + 3 对手 official score > **M3 当前最好的臂**（§0.21 的 `M3.13` 2.4293 / F2 2.5396，**不再是 2.087**），且用**重复测量**判定 | §0.21 |
| **G-B secondary（机制）** | `coins_share` > **0.186 + 0.022** | §0.16。**不能单独用来宣布成功**，只说明比赛能力来自哪里；与 score 分开报告 |
| **G-C 加分** | loot-crate solo 追平 **32.6–35.1** | 预期不达标；**不达标不作为冻结依据** |

> **0.246 这个门槛已经被 §0.20 的方法更正取代。**单次测量的门槛是**可以买下来的**：
> `M3.12` 相对 `M3.4` 单次 `+0.189` 判为不可分辨，重复 5 次后真实的 `+0.113` 却**可分辨**
> ——标准误降到 1/3。**今后对手臂一律用重复测量判定**（≥5 次重跑末 checkpoint 的对手评估）。
> 另外各臂自己的 sd 是 0.038–0.057，小于 §0.16 在 `M3.3XL` 上量到的 0.089，
> **印证了「σ 因臂而异」**。0.246 仍然只含评估噪声、不含训练方差。

## 2. 表示：`board_egocentric_v2`

`7 × 17 × 17 + 6 = 2029` 维。相对 v1 两处改动，**两处都是可证明的**。

**① 删掉 v1 的 `self` 通道。** `_egocentric_crop` 以 agent 为中心裁剪，所以那层平面对
**任何**状态都是同一个常量数组。289 个恒定输入携带零信息，测试
`test_v1_self_plane_is_the_same_constant_for_every_state` 把这件事钉死。

**② 加两个全局标量：**`visible_coins`、`crate_fraction`。两者都是当前状态可算的。

**`own_bomb` 通道做不了。**官方 `game_state` 的炸弹是 `((x, y), timer)`，
**不带所有者**（`environment.py:406`）。从动作历史重建会让 encoder 变成有状态的，
而诊断脚本 import 的正是这些函数。且单人训练时全部炸弹本就是自己的。

所有通道值落在 **1/20 网格**上，这是 §4 的前提，由测试对真实编码状态逐点断言。

## 3. 探索：为什么它被改了两次

**第一次：`E00`–`E06` 全部从 ε = 0.30 起步。**这在手工特征 + 线性/小 MLP 上从不是问题。
**随机初始化的 CNN 不同**：它的 argmax 在所有状态上近乎恒定，ε = 0.30 意味着 70% 的步
在执行同一个固定动作。smoke 直接测到：`official_wait_fraction` **0.93**、
`distinct_cells` **1.78**——一个站着不动的策略。于是有了 `E07`（ε 从 1.00 保持 100 **回合**）。

**第二次：`E07` 被 pilot 推翻。**（`diagnostics/m4_exploration_units_20260827.json`）

| | seed 1901 | seed 1902 |
|---|---:|---:|
| E07 的 100 回合 hold 内攒到的 transition | **982** | **904** |
| `replay.min_size` | 10,000 | 10,000 |
| buffer 达到 `min_size` 的回合 | **826** | **854** |
| 那时的 ε | **≈0.11** | **≈0.11** |

**第一次梯度落下时，冷启动已经没了。**根因是**单位不一致**：时间表按回合计，
`min_size` 与 `capacity` 按 transition 计，而**一个回合不是一个经验单位**——
实测它的长度在一次 run 内变化约 20 倍：

| ε | 每回合步数（实测） |
|---|---:|
| 1.00 | **9.8** |
| ≈0.3 | ≈30 |
| 0.05（已学会） | **150–210** |

这与 §0.14 的「hold 按预算比例定义」是同一类错误，低一层。

### `E09` / `E10`：按环境步计数

| | E09（冷启动） | E10（BC 热启动） |
|---|---|---|
| 起始 ε | **1.00** | **0.20** |
| hold | **10,000 步**（= `min_size`） | 同 |
| anneal | **50,000 步** | 同 |
| floor | 0.05 | 0.05 |

`hold_steps = min_size` 是刻意的：**第一次梯度步恰好在 buffer 装满时发生，且此时 ε 仍是 1.00。**

**`anneal_steps = 50,000` 是量出来的。**步计数的退火有一个回合计数没有的反馈环：
**ε 只随步数下降，而步数只在 agent 活得久时才累积。**第一版取 200,000 步，
结果 2,000 回合只跑出 18,627 步、ε 停在 **0.96**——永远逃不出随机区。
改成 50,000 后 pilot 实测：

| | seed 1901 | seed 1902 |
|---|---|---|
| 第一次梯度步 | round 1073，**ε = 1.00**，replay = 10,001 | round 1129，ε = 1.00 |
| ε 触底 | **round 3791**（60,044 步） | **round 3889**（60,215 步） |
| 触底前后每回合步数 | 12 → **50**（4×） | 同量级 |

两个 seed 相差不到 100 回合；10,000 回合的预算里还剩约 6,000 回合在 floor 上训练。

**一个副作用**：步计数时间表**无法在 config 时对回合预算做校验**（每回合几步取决于策略
活多久）。所以每条 `round_end` 现在都带 `epsilon`，由 `scripts/check_pilot.py` 事后核对。

## 4. replay 的 uint8 存储

两份 float32 的 2029 维状态是 **16.2 KB/条**，100k buffer 是 **1.6 GB／job**。
改成 1/20 网格上的 uint8 码后是 **4.1 KB/条、406 MB／job**。
`_encode_board` 对偏离网格的值**报错而不是四舍五入**，解码走查表；
测试断言真实状态 round-trip **逐位相等**。手工路线走原 float32 路径，一字节没动。

## 5. 训练诊断

每个 `round_end` 现在带：

```text
gradient_steps_this_round             这一回合真正做了几次梯度（不是 observe 次数）
gradient_steps                        累计
mean_abs_td_error_per_gradient_step   只对真做了梯度的步取平均
learner_step.replay_size              buffer 当前大小
learner_step.target_synchronised      这一步是否同步了 target 网络
learner_step.loss                     Huber 损失
learner_step.last_gradient_l2_norm    裁剪前的梯度范数
learner_step.q_mean / q_max / q_min   这个 batch 的 Q 统计
```

`updates` / `updates_this_round` 保留原语义（observe 次数），
因为 `updates_this_round == act_steps` 是 P0 回归断言，且所有已发表的 run 用的是它。

**为什么要这些**：anchor 学不动时，「buffer 一直没满」「Q 发散」「梯度被裁剪钉死」
「探索没找到东西」在旧日志里长得一模一样。

## 7. 吞吐：修正后的实测

`scripts/benchmark_cnn.py`（现在测完整 learner 路径），Apple M4 单线程：

| | CPU | Apple GPU (MPS) |
|---|---:|---:|
| **一次梯度步（完整路径）** | **20.34 ms** | — |
| ├ `fit_batch` | 8.92 ms | 10.74 ms |
| ├ `_targets`（两次前向） | **9.89 ms** | — |
| ├ `_augment`（D4） | 0.23 ms | — |
| └ `buffer.sample` + uint8 解码 | 0.15 ms | — |
| encode + inference p99 | **0.26 ms** | 3.05 ms |
| 对官方 0.5 s 上限的余量 | **1899×** | 164× |
| **env steps / 秒**（ratio 8） | **191** | 133 |
| **300 万 env steps / seed** | **4.4 小时** | 6.3 小时 |

**v1 的 2.1 小时是错的**，错因是只测了 `fit_batch`。漏掉的一半几乎全在 `_targets`——
Double DQN 固有的两次 next-state 前向（online 取 argmax、target 取值）。

### A100 有没有用

每个 env step 的成本：**梯度步 5.09 ms（97%）+ encode/inference 0.15 ms（3%）**。

网络只有 **477k 参数**、7×17×17 输入、batch 32。单次 forward+backward 的算力需求远低于
kernel launch 的调度开销，所以耗时由**每算子 dispatch 成本**决定，不是 FLOPs。
**MPS 实测比 CPU 慢**，就是这个机制的直接证据。

**对 A100 的判断（估计，不是实测——本机无 CUDA）**：CUDA 的 launch 开销低于 MPS，
A100 大概率比 CPU 快，但**只是几倍，不是几十倍**，且这个倍数在 A100 和便宜得多的卡之间
几乎没差别。

**结论：这个工作负载不是 GPU 形状的，横向并行才是杠杆。**

- 「1×A100 + 8 核」vs「32 核纯 CPU」→ **选 32 核**。
- A100 免费且核数够 → `BOMBERMAN_TORCH_DEVICE=cuda` 已接好，但**先实测再决定**。
- **不需要任何并行化改造**：`run --jobs N` 是进程级并行，`prepare` + per-job JSON 已是
  scheduler-agnostic 的，torch 默认单线程正是为了 N 个 job 不抢核。

**必须先做**：目标机器装 torch（Hetzner 的 `.venv` 只有 numpy + tqdm）。
每 job 约 **0.5 GB**。

### 为什么步长排在所有增量之前

§0.20 实测出两件事：**步长是这个项目上量到过的最大单一效应**（同宽度 1e-3 → 5e-4 是 **+8.21**），
而且更要紧的是——M3 线曾**发表过一个因此而错的结论**：`M3.8`「加容量有害」（−5.72，判为可分辨）
是**在步长固定的前提下加宽网络**造成的伪影；步长调对后同样的宽度变成 `+8.21`，
成了那条线单人最好的臂。

**在一个没调好的基座上测增量，增量的符号会反过来。**M4 的 **2.5e-4 从来没有为这个网络调过**
——它是原始 DQN 论文的步长，给的是**另一种架构、另一个优化器**（Atari 画面 + RMSProp），
写进这条路线的声明后再没动过，如今用在一个 **477,286 参数**的网络上。所以先把基座调对，再测增量。

> **更正**：早先版本说 2.5e-4 是「PyTorch 默认值」，**这是错的**——PyTorch 的 Adam 默认是 **1e-3**。

**为什么是两个臂而不是一个。**只往下试(2.5e-4 vs 1e-4)是两个点落在同一侧——
**除非你已经知道自己在最优值的哪一边，否则两个点给不出方向**，而没人知道：2.5e-4
是从别的架构和优化器上搬过来的。夹住它，一轮就定方向，而不是两轮。两臂互相独立、都对同一个 anchor 比，
核数够时可以并行，**墙钟不增加**。

三个步长都测不出差别，本身是有用的负结果——**后面每个臂都建立在「基座调对了」这个假设上**。

### 6.1 优化器与学习率时间表：已定，不做实验

| 项 | 决定 | 为什么不做实验 |
|---|---|---|
| **优化器** | **Adam**，固定 | M3 最好的臂用 Adam；DQN 的标准选择；§0.8 已经证明「Adam + 低步长 + Huber + 裁剪 + replay/target」是一个整体配方。花 4.4 小时测 SGD 的期望收益太低 |
| **损失** | **Huber**，固定 | bootstrapped target 下需要有界梯度；同上，属于已验证的稳定化配方 |
| **梯度裁剪** | **10**，固定 | pilot 实测梯度范数全程 **0.03–0.89，一次都没碰到 10**——**它当前不是约束项**，调它不会有任何效果 |
| **学习率时间表** | **`L00`（常数）**，**不预注册成臂** | `L01` 的动机是**从曲线上诊断出来的**（F2 在 2250–5000 局摆动但无趋势 = 步长对剩余梯度过大），不是先验。**触发条件**：若某臂的 checkpoint 曲线后半段出现同样形态，才上 `L01`（改一个字段） |
| **步长（level）** | **做实验**，见 2a/2b | §0.20：这是项目上量到过的最大单一效应，而 M4 的值是没调过的默认值 |

> **一个必须记下的修复。**这三项此前**在 CNN 里是写死的**，而路线在另一处声明它们——
> 两边碰巧一致，这是这类 bug 最糟的形态：什么都没错，而且它出错时也不会有人知道。
> 其中**步长那一项本来会造成一个空实验**：runtime 实现时间表的方式是每回合给
> `model.learning_rate` 赋值，而 torch 优化器在构造时就把 `lr` 复制进 param group，
> **所以 M4 上的 `L01` 臂会跑完全程、测出恰好为零的效果**——和 A07 在 n=5 上是同一种失败。
> 现在四项都从声明读取、不支持的取值 fail closed，并有测试断言时间表真的到得了优化器。

### 为什么对手暴露排到第 3

**这是一个结构性缺陷，不是猜想。**solo 训练下 `opponents` 平面与 `living_opponents`
标量**恒为零**，读它们的第一层权重**梯度恒为零**，一直保持随机初始化；
比赛评估时这些输入第一次非零，等于往网络里注入一个未训练的随机投影。

`handcrafted_v1` 有**完全相同**的结构性缺陷（它的对手相关维在 solo 下也恒为零），
而 §7.19 实测：补上它（对手训练）让 `coins_share` **18.6% → 22.0%（3.0σ，超过 0.022 阈值）**、
存活率 **3.9% → 17.4%**，代价是单人 classic −68%。
**所以手工线的证据是指向做这件事，不是指向不做。**

**为什么从零训练而不是微调**：微调更便宜也更能保住 solo 能力，但需要
checkpoint 热启动——`INITIAL_MODEL_KINDS` 明确只实现了 `behaviour_cloning`，
`"checkpoint"` 是保留且 fail-closed 的；而且它会打破本项目「每臂 fresh start」的规矩。
从零训练是零新代码、精确单因素、且与 M3.3LX↔M3.4 那一对**可直接对照**。
**若确实需要微调，代价是启用 checkpoint 热启动（约 40 行 + 测试）**，这是一个可以随时做的决定。

### BC 臂必须盯的数

示范集 `WAIT` 出现 **0** 次（150,000 状态，实测），克隆策略从不主动等待。
而 M3 的顽疾恰恰是**过度** WAIT（§0.13：117 次死亡里救命方向清清楚楚可见却选了 WAIT）。
两者可能互相治好，也可能变成「该等的时候不等」。**判定指标已更正**（§0.20 方法note 2）：`wait_fraction` **不能当判定指标**——六个 M3 臂里
死亡率最低的两个 WAIT 比例最高，最高的那个反而最低之一，**连符号都不稳定**。
改读绝对计数：**每千弹死亡**、**全程有逃生方案却仍死的次数**。`wait_fraction` 保留为描述性数字。

### 8.0b 预注册候选：`board_egocentric_v3`（**下一阶段，不是启动前的改动**）

**动机是量出来的，不是猜的。**`R02_9` 在比赛设置下 900 回合的诊断：

| | |
|---|---:|
| 总死亡 | 382（自炸 269 / 被炸 113） |
| 丢掉逃生方案那一拍存在更安全的移动 | 195 / 269 |
| **但致命方向与救命方向在 `v3` 里不可分辨** | **104 / 142 = 73.2%** |

而这个比例**随 agent 变强而上升**：单人 0% → `M3.4` 多人 34.7% → `R02_9` 多人 **73.2%**。
它已经躲开了所有"看得出来"的死法，剩下的全是 `escape_search` 结构上看不见的：
**对手的未来移动、对手的未来放弹、场上残留爆炸**。

**为什么这是 M4 可能有优势的地方。**`escape_search` 是**当前可见炸弹的确定性模型**，
它没有表示"这格现在安全、两拍后可能致命"的位置。**Q 函数只做这件事**——
在有对手的经验上做 TD 更新，"靠近一个还能放弹的对手"的代价会自己 bootstrap 回来。

**三条必须并列的限制**（不写清楚就是过度承诺）：

1. Q 学到的是**给定当前观测的历史平均危险**，不是对手意图。两个不同历史若在单帧里完全相同，
   仍然状态混叠。
2. **帧堆叠只补速度，补不了"他准备放弹"**，所以它不是这个缺口的答案。
3. 信息在输入里 ≠ 网络会学到。M4 完全可能同样学不会——但**失败的原因不同**：
   手工线是"表示不可能表达"，M4 是"表示能表达但没学到"。**后者可以靠预算/算法/容量改善，前者不能**，
   所以这两种失败在报告里的价值不一样。

**具体缺什么：**官方 `others` 是 `(name, score, bombs_left, (x,y))`，
**`bombs_left` 就在状态里**，而 `board_egocentric_v2` 的 encoder 只取 `other[3]`（位置）。
一个 `bombs_left=0` 的对手站在旁边是无害的，`bombs_left=1` 的同一个对手是致命的——
**M4 现在分不出这两种局面**，而这正是"下一拍这格会不会变致命"最有信息量的一位。

**编码方式（这一条踩过坑，写死在这里）：**

> **不能**把 `opponents` 平面直接换成 0/1 的 `bombs_left`。那会把"不能放弹的对手"
> **编码成空地**，丢掉占格信息——而占格影响可通行性与 BFS。
> 正确做法二选一：**双通道**（占格、可放弹），或**单通道三值**：
> 空地 `0`、不能放弹 `0.5`、能放弹 `1`。三值仍落在 1/20 网格上，uint8 存储不受影响。

**为什么它是候选而不是现在就改：**若把 v3 塞进对手臂，
**「多人训练分布」和「可放弹标记」会同时变，成功或失败都归因不了**。

**触发条件（预注册）：**

1. 步长定下来后，先跑**现成的 v2 对手暴露臂**；
2. 用**同一口径**复测上表的不可分辨率与死亡构成；
3. **只有当 v2 对手臂仍明显卡在这个缺口时**，才预注册并跑 v3 的**单因素**增量臂；
4. **帧堆叠排在 v3 之后**，且只在 v3 之后诊断显示缺口仍在"对手意图"上时才考虑。

> **✅ 2026-08-29 判定：第 1–3 步已执行，触发条件成立。**详见 §8.6.4。
> v2 对手臂的自炸密度是 `R02_9` 的一半（每千次放弹 8.74 对 17.70），
> 但**剩余致命转向的不可分辨率是 89.1%（41/46），高于 `R02_9` 的 73.2%**，
> `z = +2.23`，按 `|t| > 2.3` 尚不可分辨，**但绝无下降**。缺口没有被表示补上。
> **同时记下一条对 v3 不利的证据**：96% 的致命自炸在最后一拍已无任何合法移动，
> 说明相当一部分剩余死亡在几拍前就已注定，而 `bombs_left` 是一个当前帧的位。
> **v3 该跑，但它的上界很可能小于 89.1%。**

### 8.1 为什么 n 必须留在 3：一个可以精确算出来的共振

势函数塑形对 n-step target 的贡献是 $\gamma^n\phi(s_{t+n})-\phi(s_t)$——这个望远镜求和正是
策略不变性的来源。**如果势函数的瞬态刚好和 n 一样长，两端取到同一个值，这一项精确为零。**

炸弹的可观测寿命恰好是 `BOMB_TIMER + 1 = 5` 个 transition。M3 线在 `potential_v2` 上发现了
这件事（§0.22）。**我实测确认 `potential_v1`（也就是 A06，M4 用的这个）完全一样：**

| n | A06 危险项对**放弹那一步** target 的贡献 |
|---:|---:|
| 3 | **−0.257** |
| 4 | −0.217 |
| **5** | **+0.000000** |
| 8 | **+0.000000** |

**n ≥ 5 时，A06 的危险项对放弹决策的贡献是精确的零。**所以：

- **M4 的 n=3 不是「Rainbow 默认值」，而是有精确理由的**——它在炸弹寿命以下，塑形真的到得了放弹决策。
- **原来列的「若放弹安全性有问题就上 n=5」这条候选必须撤回**：那恰好会把唯一指向安全的塑形项关掉，方向完全相反。
- 有测试 `test_every_m4_arm_stays_below_the_bomb_lifetime` 守住这条线。

> **一条给 M3 线的观察（不是我这条线的结论）**：M2/M3 的 A06 臂**全部跑在 n=5**，
> 也就是说它们的危险项在放弹决策上一直是零。§7.8「n=5 优于 n=3」这个选择本身是在
> 「n=5 时危险塑形静默关闭」的条件下做出的。这是那条线要不要复核的事，
> 我没有改动任何已发表的 M2/M3 配置或它们的守卫测试。

第一次跑 `diagnose_kill_opportunities` 报了 **6/30 MISMATCH,全部是 `train1005`**。
不是随机噪声,是**一次节点停顿**:round 17 的 step 131→132 之间墙钟走了 9.3 秒,
四个 agent 全部超时。`environment.py` 的 `poll_and_run_agents` 是这样写的 ——

```
self.logger.info(f'Agent <{a.name}> chose action {action} in {think_time:.2f}s.')
if think_time > a.available_think_time:
    self.logger.warning(f'... exceeded think time ... Setting action to "WAIT" ...')
    action = "WAIT"
```

**「chose action」这一行在查表之前就写了**,超时之后世界实际执行的是 WAIT;
而且下一步该 agent 的预算已经为负,**根本不会被 poll**(`Skipping agent ...`),
连 WAIT 都不执行。`read_actions` 只认第一行,于是重放执行了 agent *想要*的动作,
真实对局执行了别的 —— round 17 step 137 差出**一格**,之后全盘不同。

| 臂 | 有超时的 job | 每 job 被强制 WAIT | 被跳过的步 |
|---|---|---:|---:|
| **opponents / train1005** | **6/6(该 seed 全部)** | 131–279 | 189–410 |
| opponents 其余四个 seed | 0/24 | 0 | 0 |
| anchor / dueling | 0/60 | 0 | 0 |

**修正后的处理不是「让重放更忠实」,而是把这些 job 排除。**
就算重放能精确复现,那几步 agent 也不在控制之中,
「有机会却没放弹」的计数量的是停顿的节点而不是策略。
三个脚本现在**默认丢弃**并打印是哪几个、丢了多少步,`--include-degraded` 可强行保留。
排除后 **24/24 精确复现**。

**这次污染没有影响主结论。**`rep10k_opponents` 里 `train1005` 是**最好**的 seed
(4.1078,臂均 3.85),说明后来那批重复测量的 job 没赶上停顿;
而被污染的是原臂的 `evaluation_summary.json`,它本来就因为选种偏差不可引用。
方向上污染是**压低**分数的,所以 §0.32 那个 3.8444 如果说错,也是错在偏保守。

### 8.6.2 死因归属:对手臂不是「少自杀」,是**几乎不死**

`attribute_deaths.py`,每臂 900 回合(opponents 排除污染后 720):

| 每回合 | **opponents** | anchor | dueling |
|---|---:|---:|---:|
| **活到回合结束** | **78.6%** | 26.4% | 21.4% |
| 死于自己的炸弹 | **13.2%** | 49.9% | 57.6% |
| 被对手炸死 | **6.9%** | 21.1% | 18.0% |
| 卷进重叠爆风 | 1.2% | 2.6% | 3.0% |

**自杀率只是表面。**对手臂被对手炸死的比例也只有另外两臂的**三分之一**,
它是在**整体上不死**,而不是单独学会了躲自己的弹。

### 8.6.3 击杀缺口是**决策**问题,不是接近问题

`diagnose_kill_opportunities.py`,对手臂 24 个 job、239,111 个存活步:

| | 数量 | 占比 |
|---|---:|---:|
| 存活步中手里有弹 | 168,021 | 70.3% |
| **此刻放弹能覆盖到对手** | **25,526** | **15.2%**(占持弹步) |
| 其中放完还能逃 | 25,349 | **99.3%** |
| **其中它真的放了** | **1,543** | **6.0%** |
| `rule_based_agent` 自己的触发条件(对手一步之内) | 10,403 | 6.2% |
| 其中它放了 | 570 | 5.5% |

**§7.26 留下的那道选择题有答案了。**它**不是**「几乎从不站在能炸到对手的位置」——
15.2% 的持弹步都能炸到,而且 **99.3% 的情况下放完还有活路**。
**它站在那里,能安全地放,而它不放。**这是决策问题,
所以**对放弹做塑形是有靶子的**,不是无处着力。

对照 `rule_based_agent` 自己的触发条件(对手在一步之内):这种步占 6.2%,
它只在其中 5.5% 放弹 —— 和总体的 6.0% 几乎一样。
**它对「对手就在旁边」这件事没有额外反应。**

### 8.6.4 §8.0b 的触发条件:**成立**,缺口没有被表示补上

`diagnose_bomb_escape.py`,对手臂 24 job / 720 回合,对照 M3 `R02_9`
(`diagnostics/escape_r02_9_tourney_20260828.json`,900 回合)。

**先说口径,否则这张表会被读错。**「不可分辨」量的是
**`handcrafted_v3` 的 escape 条目**能不能把致命那一步和能活那一步分开。
它是一把**固定的尺子**,不是 M4 实际看到的输入(M4 看 `board_egocentric_v2`)。
所以它回答的是「**杀死 agent 的是哪一类局面**」,不是「M4 的表示够不够用」。
正因为尺子固定,两条线才可比。

| | M3 `R02_9` | **M4 opponents** |
|---|---:|---:|
| 放弹总数 | 15,199 | 11,899 |
| 致命自炸 | 269 | **104** |
| **每 1000 次放弹的致命自炸** | **17.70** | **8.74** |
| ├ 放下去时就已经无解 | 3.29 | **2.77**(−16%) |
| └ 放下去有解、后来丢了 | 14.41 | **5.97**(−59%) |
| 丢解那一拍还有更安全的移动 | 195/269 | 68/104 |
| 可比较的致命转向 | 142 | 46 |
| **其中在 `handcrafted_v3` 里不可分辨** | **73.2%** | **89.1%** |
| 在 `handcrafted_v1` 里不可分辨 | — | 46/46 = **100%** |

**三条结论,按可信度排序。**

**一、M4 的自炸密度是 M3 的一半**(8.74 对 17.70 每千次放弹),
而且**几乎全部的改善来自「放完之后逃得掉」**(−59%),
「不放明知逃不掉的弹」只改善了 16%。
**CNN 学到的是逃生,不是放弹前的可行性判断。**

**二、剩下的死亡更集中在那个缺口里,而不是更少。**
89.1% 对 73.2%,`z = +2.23` —— 按本项目 `|t| > 2.3` 的判据**尚不可分辨**,
但方向明确:**没有任何证据说这个比例下降了。**
§8.0b 记的那条上升曲线(单人 0% → `M3.4` 多人 34.7% → `R02_9` 多人 73.2%)
在 M4 上**继续**,而不是被表示打断。

**三、触发条件成立。**§8.0b 写的是「**只有当 v2 对手臂仍明显卡在这个缺口时**,
才预注册并跑 v3 的单因素增量臂」。它仍然卡在里面,
所以 **`board_egocentric_v3`(`bombs_left` 双通道或三值单通道)可以预注册**。

**但要同时记下一条对 v3 不利的证据。**致命自炸里
**100/104(96%)在最后一拍已经没有任何合法移动**,
且 46/46 的致命转向在 `handcrafted_v1` 的危险特征里**完全**不可分辨。
这说明相当一部分剩余死亡是**几拍之前就注定**的,
而 `bombs_left` 是一个**当前帧**的位 —— 它能解释「这个对手下一拍能不能放弹」,
解释不了「三拍前我就该往另一边走」。
**v3 该跑,但它的上界很可能小于这 89.1%。**

补充两个次要观察:

* 「有解却仍然死掉」只有 **3 例**(M3 是 22),而且三例都是**世界拒绝了那步移动**
  (`unexplained`,即被对手同拍抢占)。**这一类基本被消灭了。**
* `A06` 塑形把 WAIT 排在所有更安全移动之上的比例,M3 是 21.0%,M4 是 **15.1%**;
  平均 `WAIT` 减最优安全移动为 **−0.1328**。塑形在 M4 的轨迹上更少给出错误排序。

## 10. 一个被自己的实测推翻的结构假设（记录用）

设计时论证：「爆炸十字差一格就是生死，stride 会模糊格位对齐，早期层必须全分辨率」。
**实测（batch 64，单线程）：**

| 候选 trunk | flatten | 参数 | 梯度步 |
|---|---:|---:|---:|
| **A 两次早 stride（采用）** | 1600 | 477k | **32.4 ms** |
| B 三层全分辨率 + 末端 s2 | 5184 | 1.43 M | **104.3 ms** |
| C 两层全分辨率 + s2 + 一层 | 5184 | 1.40 M | 60.3 ms |
| D 三层 32 通道全分辨率 + s2 | 5184 | 1.38 M | 64.5 ms |
| E 一层全分辨率 + 两次 s2 | 1600 | 514k | 49.9 ms |

3.2 倍吞吐差就是 3.2 倍 env steps。而且论证本身比听起来弱：窗口 egocentric 且尺寸固定，
**stride 网格相对 agent 的偏移是固定的**，右边一格永远落在下采样图的同一位置——
这是一致下采样。**但不能说「没有 aliasing」**，只能说在这个固定网格下，
CNN 可以在通道维上分开它们，且当前成本收益更好。

保留一条反向证据：**同一份示范集、同样 3 epoch 的行为克隆，B 的验证准确率 0.911，
A 是 0.897（+1.4pp）**。分辨率确实值一点东西，只是要付 3 倍。

### 11.5.3 归档的三条操作规矩

1. **`--slim-copy` 的目标写父目录**,不要带 run 名 ——
   `rsync ... run_archives/` 而不是 `run_archives/<run>/`,否则会**嵌套而不是合并**。
   §7.17 就是这么把 `m3_3lx_oppeval_20260826` 串成 M3.5 结果的。
2. **拉完跑 `verify_run_archives.py --runs-root run_archives`** ——
   它按 run 内部记录的 id 核对目录名,文件名相同不代表内容相同。
3. **集群的 `/tmp` 不跨登录节点共享。**中转目录写 `$HOME`,不要写 `/tmp`。
4. **不用 `rsync` 拉 `runs/`。**几千个小文件必然中途断在
   `transport endpoint shutdown (108)` 或 broken pipe,而**断了的 rsync 会留下一个
   看起来完整、其实缺文件的目录** —— 这就是 `rep10k_opponents` 一开始少了
   `experiment_config.snapshot.json` 的原因。**集群上 `tar` 成一个包再 `scp`,
   解开后数个数。**
5. **已经是 `.gz` 的文件用 `tar cf`,不要 `tar czf`。**
6. **本机跑诊断用 `.../envs/ml_homework/bin/python`。**默认 `python` 是 conda base,
   没有 numpy;而 `repeat_measure.py` 恰好不 import numpy,所以「上一条命令能跑」
   完全不能推出「这条也能跑」。
